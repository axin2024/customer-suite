# 客户成功与续约

## 从合同到续约

1. 本公司经理打开「客户成功」，给有效合同分配客户成功岗位的成员。
2. 负责人采集健康度。每份快照保留原始客户版本、当期合同版本、未解决的服务和交付计数、扣分理由、采集人及 UTC 时间。负责人交接后，现任人员可查阅历史。
3. 经理在「续约工作台」扫描到期窗口。系统以签约公司、合同和有效版本的到期日为键，生成一份续约记录和一条销售商机。重复请求和并行扫描共用这个约束。签署补充协议并改变到期日后，扫描生成新周期，并结束旧的开放周期。到期日相同的修订保留既有周期。
4. 客户成功负责人安排跟进，选择续约成功或者记录流失分类与原因。成功时登记签署凭据编号。续约和商机阶段在同一事务更新，商机保留阶段历史。新合同仍按签约流程归档。
5. 发送续约提醒时，选择联系人、渠道与内容。触达工作单保留操作者、状态、拦截原因、尝试次数与渠道回执。入队和处理时都检查合同周期、客户状态及联系人同意。

模型 v1 从 100 分扣减。冻结扣 100 分。已终止或已到期扣 45 分，30 天内到期扣 15 分。每份未解决工单扣 3 分，其中已升级额外扣 10 分，服务扣分合计最多 35 分。每项未解决交付问题扣 5 分，合计最多 25 分。80 分及以上为「健康」，60–79 分为「需关注」，其余为「有风险」。客户冻结后，合同工作台立即显示风险与暂停状态，原快照仍可按历史版本查询。

## 定时处理

按公司为下列 CLI 命令设置定时器。使用拥有该公司经理权限的服务账号编号。处理进度可以从「续约工作台」及操作回执查询。

```sh
docker compose exec -T web php bin/crm.php renewal-scan <公司编号> <经理编号> 30
docker compose exec -T web php bin/crm.php outreach-due <公司编号> <经理编号>
```

每次扫描处理最多 50 份候选合同，返回 `more` 供调度器判断是否继续。触达每批最多处理 20 条待办。渠道结果不确定时按分钟退避，间隔从 1 分钟逐步加长到 256 分钟。客户冻结、撤回同意或联系人变更时，工作单显示已拦截，等待负责人复核。解除冻结后，负责人可重试原工作单。联系方式或联系人版本变化时，核对同意后新建工作单。

## 嵌入渠道网关

默认配置 `CRM_OUTREACH_MODE=replay`。工作单显示「回放完成」并附带合成回执。需要真实渠道时，在部署端配置 `CRM_OUTREACH_MODE=webhook`、`CRM_OUTREACH_WEBHOOK` 和 `CRM_OUTREACH_SECRET`。地址为受信任的 HTTPS 接收端，密钥至少 32 字节，由部署方保存。工作单在入队时绑定回放或 webhook 模式。

请求使用 `POST`，正文是带 `idempotency_key`、`channel`、`address`、`message` 的 JSON。渠道同意允许时才读取并向网关提交当前地址。工作单和操作回执无需存储地址。

- `Idempotency-Key` 与正文的 `idempotency_key` 相同。
- `X-CRM-Timestamp` 为 UTC Unix 秒。网关应检查时间窗口，并校验 `X-CRM-Signature` 中 `sha256=` 后的十六进制值。签名输入为「时间戳、小数点、原始正文字节」，算法为 HMAC-SHA256。
- 网关应以幂等键持久化接收结果，并在重试时返回同一回执。接收成功返回 HTTP 2xx 及 JSON，如 `{"idempotency_key":"原始幂等键","reference":"gateway-001"}`。CRM 记录的是渠道接收回执。网关负责后续实际发送和投递跟踪。
- HTTPS 失败、非 2xx、错误的幂等键以及不完整的回执会进入待重试。渠道处理中断后，用原幂等键向同一部署网关查询或重试。

## 测试

`tests/customer-success.php` 在隔离 MySQL 中验证 AC-13 和 AC-14，并覆盖改派、撤权、流失与续约结果、渠道回放和退避。`tests/outreach-gateway.php` 使用自行生成的临时 TLS 证书、本机接收端及合成地址，验证签名、匹配回执和不确定结果处理。HTTP 工作台测试检查岗位页面、健康度来源、表单与拦截说明。
